ENTRY 1   2026-10-13

ASKED
  Turn the autograd engine into a full website product, built in phases.
  The idea: a tool that lets people visualise deep learning (backprop,
  optimizers, layer sizes, activations, skip connections, reverse vs forward
  mode, activation checkpointing). End goal: drag and drop nodes, connect
  them, and watch learning happen; a transparent glass over PyTorch-style
  libraries; a data-flow diagram of neural network training. Little
  conceptual text in the first draft. Draft a 5-phase plan, starting from a
  deep learning syllabus, with constraints (no ResNet-50), core in C++.
  Read the current code, micrograd, and PyTorch first.

ANSWERED
  What was read
    - This repo: Tensor.hpp/.cpp, Ops.hpp/.cpp, Bindings.cpp, CMakeLists.txt,
      tests/test_engine.cpp, summary.txt.
    - micrograd engine.py and nn.py.
    - PyTorch torch/csrc/autograd/engine.cpp and torch/utils/checkpoint.py.

  State of the engine today
    micrograd in C++: 8 scalar ops, a backward closure per node, recursive
    topological sort, no optimizer or layers. Four blockers:
      1. Scalar only: every op touches element [0].
      2. Backward closures are opaque: cannot be stepped, serialised, listed
         in a palette, or run in forward mode.
      3. Leak: each closure captures its own output node.
      4. Tests always exit 0 and have no finite-difference check.

  Central idea
    The engine emits a step-by-step trace of everything it does. The website
    is a viewer and editor for that trace.

  Architecture
    - C++ core compiled to WebAssembly, run in a Web Worker. No server.
    - Op registry: each op declares forward, vjp, jvp, shape_infer.
    - Executor in PyTorch's style: dependency counts, ready queue, saved
      tensors released explicitly.
    - Three zoom levels: scalar, tensor, module.
    - Python bindings kept only as a test oracle against PyTorch.

  Constraints (proposed, to be measured)
    about 100k parameters per model, about 64k elements per tensor, about
    200 nodes on canvas, a train step under 16 ms, float32 on CPU, small
    bundled datasets. "ResNet" means 3 to 6 residual blocks on small data.

  Syllabus
    Computation graph and chain rule; reverse vs forward mode; tensors and
    broadcasting; activations; losses; initialisation; optimizers and
    schedules; training pathologies; layer sizes; skip/concat/weight
    sharing; regularisation; normalisation; convolution and pooling; memory
    and checkpointing; attention (stretch).

  Five phases (later merged into two, see entry 3)
    1 Engine, 2 Read-only viewer, 3 Live training, 4 Builder, 5 Depth and
    launch.

  Also noted
    - Similar tools exist (TensorFlow Playground, CNN Explainer, Transformer
      Explainer, Netron), so "no tool exists" is not quite right.
    - The CLAUDE.md found on the Desktop describes a different project
      (AirStay) and was ignored.

ASKED
  How would Andrej Karpathy build Phase 1 end to end? Work out the HLD, LLD
  and function signatures. Cross-verify with CNN Explainer, Netron,
  Transformer Explainer, TensorFlow Playground. Finalise a fault tolerant,
  reliable design: signatures, data flow, everything except the in-depth
  implementations. Implement that, and record it in progress.txt.

HOW THE REQUEST WAS READ
  "Everything except the in-depth implementations" was taken to mean: write
  the design, and put every data structure and function signature into real
  code that compiles, with bodies left as stubs. Small utilities that the
  skeleton's own tests need were implemented for real. If the intent was
  only a document, or a full implementation, this entry is where to correct
  it.

ANSWERED
  1. Approach
     Nobody can speak for Karpathy, so the design follows the habits visible
     in micrograd and ConvNetJS: small flat code, plain structs and free
     functions, the simplest correct mechanism, one table of ops, every op
     checked against finite differences and PyTorch, and overfit one tiny
     case (moons) before building anything else.

  2. What the design changed from PLAN.md, all simplifications
     - Event trace  ->  a schedule of micro-steps computed at compile time.
       The UI gets the whole timeline up front; scrubbing backwards is exact.
     - Strides and views  ->  always-contiguous tensors.
     - Ready-queue executor  ->  reverse node order (nodes are already
       topological because an input must have a smaller id).
     - Views into WASM memory  ->  statistics computed in C++, full tensors
       copied only for the selected node.
     - Per-step allocation  ->  everything allocated once at compile.
     - Ops that throw  ->  floating-point rules plus nan/inf detection that
       names the node.
     - Bitwise native/WASM equality  ->  agreement within tolerance.

  3. HLD
     Page (main thread): GraphSpec, one AppState with a reducer, React Flow
     canvas, canvas charts, EngineClient.
     Worker: dispatch, bridge, WASM engine.
     Engine: capi -> Session -> two Programs (train batch, eval batch)
     sharing one ParamStore -> Exec -> op kernels; Optimizer; Dataset.

  4. Data flow
     GraphSpec -> validateSpec -> toBuildPlan -> addNode calls -> compile
     (shapes, limits, buffer layout, schedules) -> Session -> page receives
     node shapes and schedules.
     Stepping: begin / advance / seek(replay from snapshot) / read.
     Training: worker runs N steps, posts one Frame, waits for the ack.

  5. Fault tolerance (full table in DESIGN_PHASE1.md section 7)
     - Everything is checked at compile time; after that the only runtime
       failure is a non-finite number.
     - Nothing is allocated while running.
     - A training step is a transaction: snapshot at start, rollback on
       fault, so a nan never reaches the parameters.
     - No exceptions; every function returns a status with node and slot.
     - Handles carry a generation, so stale handles are rejected.
     - Client watchdog restarts a crashed or hung worker and rebuilds
       sessions from spec and seed; after repeated failure the page falls
       back to recorded presets.
     - One frame in flight, so a slow page cannot make messages pile up.

  6. Cross-check against existing tools (their source was read today)
     TensorFlow Playground   5 files; forwardProp/backProp/updateWeights as
                             free functions; 100x100 boundary grid drawn one
                             pixel per sample; state and seed in the URL
                             hash. Taken: all four. Different: we compute in
                             a worker and roll back diverged runs.
     CNN Explainer           runs the model once, builds its own node/link
                             graph from all outputs, then draws. Taken:
                             draw only from a complete snapshot (Frame).
     Transformer Explainer   ONNX Runtime Web plus five precomputed
                             examples. Taken: recorded presets shown before
                             the engine loads and when it cannot run.
     Netron                  format-independent graph model; layout in a
                             cancellable worker; one error screen. Taken:
                             one error banner, client owns the worker.
     The check changed four things: grid default of 100, recorded-preset
     fallback, single error banner, snapshot-per-frame drawing.

  7. Files created, not committed
     product-dev/DESIGN_PHASE1.md   the design
     engine/include/ag/             core rng graph ops program exec optim
                                    data scalarize session (.hpp), capi.h
     engine/src/                    one .cpp per header
     engine/tests/test_skeleton.cpp
     engine/CMakeLists.txt
     web/src/graph/spec.ts          GraphSpec, validation, build plan
     web/src/engine/protocol.ts     18 request types, Frame, Stopped
     web/src/engine/client.ts       EngineClient and Session interfaces
     web/src/views/contracts.ts     AppState, actions, chart and component
                                    signatures
     Changed: root CMakeLists.txt (adds engine/), PLAN.md (points at the
     design; 1A work list and exit criteria brought in line with it).

  8. What is real and what is a stub
     Implemented: status and error type, shapes and the broadcasting rule,
     PCG32 rng, graph building with arity and reference checks, the op
     table (names, arity, categories), C API metadata functions.
     Stubs: all 23 op kernels, compile, the executor, optimizers, datasets,
     scalarize, session, 27 of 37 C API functions, and the whole web

  9. Verified
     - Engine skeleton compiles with g++ -std=c++20 -Wall -Wextra -Wpedantic

     - The original scalar engine still builds and its 44 checks pass.

ENTRY 6   2026-10-14
------------------------------------------------------------------------
ASKED
  Find errors in this in depth: overflows, the graph not building
  properly, or anything else, and fix them.

ANSWERED
  1. Method
     Read every path where outside numbers enter (shapes, attributes, the
     C API, the bridge), every float-to-int and double-to-float
     conversion, every allocation, and every state transition in sessions
     and views. Each suspected bug was reproduced before it was fixed, and
     each now has a test. The engine suite also runs with
     undefined-behaviour traps on.

  2. Bugs found and fixed (full table: DESIGN_PHASE1.md section 13)
     Engine
     - Shape size overflow: [65536]x4 wrapped to 0 elements, passed the
       limit, compiled with a zero-size buffer.
     - Histogram int(nan) for values near the float limit (undefined; can
       trap in WASM). Out-of-range double-to-float conversions in sums,
       losses and norms (undefined). Both now saturate safely.
     - nan/inf attributes were accepted; now refused at the node.
     - A negative uniform init scale gave all zeros.
     - Out of memory in WASM aborted the engine. A first fix (ask malloc,
       then allocate) did not work because the compiler deleted the
       unused malloc; found by testing, not assumed. The arena is now
       allocated with calloc and kept, so a full heap is an OutOfMemory
       error and the engine keeps working.
     - Any error during a stepped training pass rolled parameters back to
       a stale snapshot, undoing real training. Now only a nan does.
     - Changing the optimizer mid-step left a step that could not be
       undone. Now that step is cancelled.
     - The C API had no node cap per graph and no handle-table cap.
     Web
     - The bridge leaked engine sessions when a later read failed; read
       the step counter as signed; returned uninitialised grid memory.
     - The worker's step limit counted the run, not the session.
     - Switching zoom in forward mode flashed a false error.
     - The race button stayed on Pause after the race ended, and racing
       continued in a hidden tab.

  3. Graph building
     Every op case now also builds its single-number graph and must give
     the same loss and gradients, plus new edge cases: an input used
     twice, x @ x-transposed, rank-4 broadcasting, keepdim, reshape to a
     scalar. All pass; no graph-building bug was found. If you have seen
     a specific graph build wrongly, tell me which preset and what you saw.

  4. Verified
     154 native checks plus 33 skeleton checks; the same suite with
     undefined-behaviour traps; PyTorch comparison unchanged; WASM agrees
     with native to 1.4e-7 and now survives running out of memory; 13 web
     unit tests; browser smoke test of all presets including the zoom
     switch. Recorded runs regenerated byte-identical, so no numbers
     changed.
